# DO-178C DAL-A

## Status, first

**IronSocketLayer is not DO-178C certified.** Certification is granted to an
applicant's airborne system by a certification authority, on the basis of
life-cycle data produced under approved plans, with independent verification.
A library cannot hold it on its own. What this repository can do is be built
so that producing that data for it is tractable, and supply the parts of the
data that belong to the software itself. This document says which parts exist,
how they are kept honest, and what an applicant must still produce.

## The DAL-A profile

`Profile::DalA` exists to shrink what must be verified:

| | DAL-A profile | Default profile |
|---|---|---|
| Cipher suites | TLS_AES_256_GCM_SHA384 | 3 |
| Groups | secp384r1 | 4 |
| Signature schemes | ecdsa_secp384r1_sha384 | 11 |
| Authentication | mutual, mandatory (config refuses otherwise) | server only |
| FIPS gate | on | off |
| Session resumption | off (one handshake path) | on |

One suite, one group and one scheme remove whole decision branches from the
executed code, which reduces the MC/DC obligations for a given configuration.
The rest of the library stays present, so it is **deactivated code** under this
profile, and the applicant's plans must say how it is handled (DO-178C
§6.4.4.3.d). Unused suites, groups and schemes can also be removed at compile
time by a project fork, since the negotiation code is table-driven.

## What an applicant must still produce

Stated plainly, because an agent or a program manager reading this must not
conclude the work is done:

1. **Plans.** PSAC, SDP, SVP, SCMP, SQAP and the standards they reference,
   approved by the certification authority. None are included here.
2. **Structural coverage to MC/DC (A-7.5 to A-7.7), with object-code
   considerations.** Not yet measured. The approach intended is LLVM's MC/DC
   instrumentation on the requirements-based tests only, followed by analysis
   of every uncovered condition, which then gets a requirement and a test or is
   justified as deactivated code.
3. **Tool qualification (DO-330).** The Rust compiler, and any coverage tool
   whose output is relied upon, need qualification data or an alternative
   argument. None is provided here.
4. **Independence (A-3 to A-7 at DAL-A).** Reviews and verification must be
   performed by someone other than the author. This repository's tests were
   written alongside the code.
5. **IronCrypto's life-cycle data.** Every cryptographic function is
   IronCrypto's. A DAL-A system using IronSocketLayer needs the same evidence for
   IronCrypto.
6. **Dynamic memory.** The engine uses `alloc` (`Vec`, `Box`). Every allocation
   is bounded, but many DAL-A programmes prohibit allocation after
   initialisation. Either the programme's standards accept bounded heap use
   with an analysis of worst-case consumption, or a fixed-capacity build is
   needed. That build is planned, not implemented.
7. **Target testing (A-6.5).** Tests run on a host. The `no_std` build is shown
   to compile for Cortex-M (`thumbv7em-none-eabihf`). Execution on the target
   hardware is the applicant's.
8. **Robustness beyond this suite.** Coverage-guided fuzzing exists
   (`fuzz/`: six libFuzzer targets under AddressSanitizer, covering the
   handshake-message and record decoders, X.509/CRL/OCSP/ECH parsing, and whole
   TLS client, TLS server and QUIC server connections), and CI runs each target
   briefly. Neither the harness nor libFuzzer is a qualified tool, and a clean
   run shows only that no crash was found, not that none exists.
9. **Timing side channels.** A review of IronSocketLayer's own code
   (2026-09-29) found every comparison of a peer-supplied value with a secret
   or server-held one going through `ic_core::ct::verify`: Finished MACs, PSK
   binders, ECH confirmation, pins, ticket key names, the replay guard and the
   HelloRetryRequest cookie. The cookie compare was made constant time in that
   review, though the cookie is not secret. Secret-holding types
   (`Output`, `SecretVec`, shared secrets) do not implement `PartialEq`, so an
   `==` on them does not compile. The one leak found was record padding
   removal, which stopped at the last non-zero byte and so took time
   proportional to the padding. It now scans the whole record (`REQ-REC-007`),
   following IronCrypto's convention: every data-dependent decision is an
   `ic_core::ct::Choice` released through `black_box`, and `leading_zeros`,
   not constant time without LZCNT, is avoided. Its x86-64 release code was
   inspected: it branches only on the record length. Other targets' code has
   not been inspected, and no statistical timing test (dudect-style) has been
   run, so elsewhere this rests on the source and the `black_box` barriers. The primitives' own constant-time properties are IronCrypto's,
   and its SECURITY.md records where they do not hold.

## Why Rust helps, and where it does not

The type system and `#![forbid(unsafe_code)]` remove whole classes of
defect: out-of-bounds access, use-after-free, data races. A C library has to
argue their absence by analysis for every function. They do not remove the
need for any DO-178C objective, and a qualified toolchain is still required
before those guarantees count as certification credit.
